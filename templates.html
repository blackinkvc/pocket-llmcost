01

四条使用规则

只填空，不改骨架

表头是给横向对比用的。删一列、加一行，两份结果就对不上了，等于白填。

不知道就留空

沿用全站三态：真值 / 空 / n/a。空表示「没查到」，n/a 表示「这项不适用」，两者不能混。

每份都要有出处

没有出处栏的模板只能当草稿。数字可以旧，但必须能说清是从哪来的。

至少填两份

单份填完只是笔记；两三个场景并排，差异才会自己跳出来，模板的价值在这里。

这几套模板是顺序递进的：先选型（定下用哪个模型），再算成本（值不值得用）， 然后写工具定义（怎么接进 Agent），接着设计评测（怎么证明它行）， 部署时对一遍核对单，最后把结论按投稿模板沉淀下来。

02

模型选型矩阵

六个维度，缺一不可。能力看榜单但要注明是哪个榜，价格看实际用量结构而不是官方标价， 上下文看有效长度（能稳定用到的）而不是标称值。

维度填什么常见的坑
能力榜单名 + 分数 + 样本量拿单一榜单当结论；不看样本量和置信区间。
价格输入 / 输出 / 缓存命中 三档单价只看输出价；忽略缓存和批量折扣。
上下文有效长度 + 超长时的退化表现把标称 200K 当能稳定吃 200K。
延迟首 token 时间 + 输出速度（tok/s）只测平均值，不看 P95 长尾。
部署API / 自托管 / 端侧，三选一没算自托管的运维人力。
锁定协议兼容性 + 换模型改动量把厂商特有参数写进业务代码。

03

成本估算单

先把量算清楚，再乘单价。顺序反了，估算会差一个数量级。

FORMULA月度口径
月成本 ≈ 日请求数 × 30
        × ( 平均输入 token × 输入价
          + 平均输出 token × 输出价 ) / 1e6

有缓存命中时：
  输入侧成本 × (1 − 命中率) + 输入侧成本 × 命中率 × 缓存折扣

要留的三个余量：
  重试与失败重放   ×1.05 ~ ×1.15
  评测 / 灰度流量   ＋10% ~ 20%
  多轮对话的上下文增长（第 10 轮不是第 1 轮的量）
要填怎么取注意
日请求数线上真实日志别用「预计用户数 × 人均次数」拍出来。
平均输入 / 输出按场景分开统计混在一起算会把长文场景的低频高耗摊平。
峰值倍数P95 日请求 / 日均限流按峰值设计，预算按均值算，两本账。
缓存命中率实测，不要估系统提示稳定才有高命中，改一个字就掉。

精确到分的算价可以直接用 AI 天梯榜 & 价格追踪 里的口径， 那里每条价格都挂了来源。

04

Agent 工具定义

工具定义最容易写错的地方是 description：它不描述工具「是什么」， 而要告诉模型「什么时候该用、什么时候别用」。参数用枚举收敛，别留自由文本。

JSON单工具骨架
{
  "name": "search_orders",
  "description": "按订单号查询订单状态。仅当用户提供了订单号、且问的是物流或退款进度时使用；用户只说商品名时先调 search_products。",
  "input_schema": {
    "type": "object",
    "properties": {
      "order_id": { "type": "string", "description": "订单号，形如 SO-2026-000123" },
      "fields": {
        "type": "array",
        "items": { "enum": ["status", "logistics", "refund"] }
      }
    },
    "required": ["order_id"]
  }
}

写清边界

「什么时候不用」比「什么时候用」更能减少误调用。

参数要收敛

能枚举就别放开自由文本；能必填就别给默认值。

错误要结构化

返回「错在哪、能不能重试」，而不是一句 500。

一个工具一件事

「查询并修改并发送」这种复合工具，模型永远用不对。

05

评测设计卡

评测最容易糊弄自己的地方是「我觉得比上一版好」。先定判卷人，再定样本，最后才看结果。

要素可选建议
判卷人人 / 强模型 / 可执行测试有测试就用测试，这是唯一不会疲劳的判卷人。
样本量≥ 30 条起步少于 30 条的差异基本是噪声，别下结论。
样本来源真实日志 / 构造用例两者都要：真实日志看分布，构造用例盯边界。
通过标准全对 / 关键项对写清楚哪些错可以接受，否则结果不可用。
顺序偏差AB / BA 交替强模型判卷偏好先出现的答案，务必换序跑一遍。
留档原始输出 + 时间 + 版本只存分数等于没做，一个月后无法复现。

06

本地部署核对单

六条，逐条打勾。任何一条没过就先别上生产。

#核对项判据
1显存够不够权重 + KV cache + 框架开销，再乘 1.2 余量；按上下文拉满算一次。
2量化与引擎匹配GGUF 配 llama.cpp、AWQ/GPTQ 配 vLLM，混着用会静默降速。
3长上下文不炸把上下文填到上限跑一轮，看 KV cache 是否把显存吃穿。
4首 token 可接受冷启动和热启动分别测，别只报热的。
5许可证允许商用条款、用户数上限、是否要求署名，逐条看过原文。
6异常能自恢复断电 / OOM / 重启后能否自动拉起，日志在哪。

显存怎么估、各档位能跑多大的模型，见 本地部署； 卡本身的带宽与算力，见 硬件。
