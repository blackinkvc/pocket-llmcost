存储与查询链路：5 类存储、查询入口、混合检索、重排与 Grounded 生成

① 为什么 RAG 后端要用 5 类存储（第 5 张图）：核心是「职责分离：不同存储，各做各的事」，千万级系统里不同数据的访问方式完全不同，强行塞进一种数据库后面通常会很难受。

本卡合并 4 张图（5 类存储 / 查询入口 / 混合检索 / 重排与生成），与 T050 写入链路、T052 生产保障并列。

  • 对象存储（S3 / OSS）：放原始文件与解析结果，便于回放和重新处理
  • 元数据数据库（Postgres）：存文档状态、ACL、任务状态、版本信息
  • 向量库：存 Embedding 向量，负责近邻召回（封面补：分片存储、ANN 检索）
  • 关键词索引（OpenSearch）：做 BM25 / 倒排检索，擅长术语和精准关键词
  • Redis / 语义缓存：命中相似问题时直接返回，降低重复查询成本（封面补：热点查询）

为什么不能只用向量库（图面三条）：① 原始文件不适合放进向量索引——向量索引只存向量及少量元数据，不适合存大体积原始文件（PDF、Office 等）；一旦需要回放、重新解析或更换模型，无法从向量库恢复原始数据。② 关键词检索与结构化元数据查询各有擅长——向量检索擅长语义相似，但不擅长精确关键词（产品型号、错误码等）；文档状态、ACL、版本等结构化信息更适合在元数据数据库高效查询与管理。③ 热点缓存、任务状态、权限信息也不是向量库的强项——热点问答需要低延迟缓存命中，Redis 更合适；任务状态（解析 / 向量化进度）和权限控制（ACL）需要高并发、强一致的事务能力，向量库并不擅长。图面特别说明「这不是固定答案：中小规模系统可以合并技术栈，但数据量一大，分层存储往往更稳、更好扩展」。

② 用户提问后，系统先做哪些判断（第 6 张图）：不是每个问题都该立刻塞进 LLM。查询入口 4 步：① 带上上下文的请求进入系统（用户问题、租户 / 角色 / 权限范围、当前知识库版本，系统据此决定后续策略）→ ② 语义缓存（先看是否命中过去的相似问题，命中后可直接返回结果或候选证据，适合高频、重复问题）→ ③ Query Rewrite（把口语化问题改写得更适合检索、补全省略信息如时间 / 对象 / 范围、统一术语表达让召回更稳定）→ ④ Query Routing（区分问题类型分别进入：文档问答 → RAG 检索链路 / SQL 与指标查询 / 外部动作（调用工具或业务系统））。

缓存不能只看相似度（图面特意单列）：语义相似只是缓存命中的必要条件，还要综合 租户（确认缓存结果所属租户 / 组织是否一致，避免跨租户数据泄露）、权限范围（校验当前用户角色与权限范围，确保返回内容可访问）、知识库版本（检查缓存结果对应的知识库版本是否最新，避免返回过期内容）三者，才能安全、准确地复用。结论：「查询入口做得越细，后面的检索和生成越轻松；很多系统响应慢、答非所问，问题其实早在入口就埋下了」。

③ 2 亿 Chunks 怎么把相关内容找出来（第 7 张图）：向量检索擅长语义相似，BM25 擅长术语与关键词，真正稳的方案通常两路一起上。

  • A 向量检索：问题 → 编码成向量 → 从向量库召回 Top 100 → 候选集 A；擅长语义相似和表达变化，可在表述不同的情况下找到同一意图的相关内容
  • B BM25 / 关键词检索：文档 + 关键词 → 倒排索引 → 召回 Top 100 → 候选集 B；擅长产品名、术语、版本号、错误码，对关键词精确匹配更敏感
  • C RRF 融合（Reciprocal Rank Fusion，倒数排序融合）：两路结果合并、去重 + 重新排序得到融合候选集；不强行比较不同分数的绝对值，目标是保留更稳的候选集合。图面称它「简单有效的多路检索结果融合方法」
  • D 权限过滤要尽早做：检索阶段就要带上 ACL / tenant filter，「不要等内容进了 Prompt 再删」
  • 为什么混合检索更稳：语义检索能找同义表达 + BM25 能抓精准关键词 → 两者互补、减少漏召回，为后续重排提供更好的候选池。图面一句提醒：海量文档场景里，召回阶段最怕「本来有答案，但系统根本没把它找出来」

④ 召回之后，为什么还要重排（第 8 张图）：召回只是把「可能相关」的内容捞上来，真正决定回答质量的是后面的证据筛选与生成约束。

  • 候选集合：混合检索后拿到约 100 个候选片段，里面可能有相关，也可能只是看起来像
  • Cross-encoder 重排：逐条比较问题与候选片段，打出更细的相关性分数（图面示意 0.96 / 0.93 / 0.88，属示意值），选出最值得进上下文的少量证据
  • 保留前 8 个证据片段：不是越多越好；上下文过长会抬高成本，也会稀释重点
  • Grounded Prompt：只允许基于检索到的证据作答；证据不足时要明确说明、而不是硬编；回答中附上引用标记，方便追溯来源和验证准确性。图面给了 Prompt 示例：「请基于以下检索到的证据回答问题，只使用这些证据中的信息；若证据不足，请明确说明。请在回答中标注引用：[证据1][证据2][证据3]」
  • 流式回答：LLM 根据证据生成答案（在满足约束的前提下进行归纳与表达），同时返回引用来源；引用最好能落到 doc_id / 版本 / 段落位置。图面答案示例带 [1][2][3] 引用角标
  • 这一层解决的三个核心问题：把「找得到」变成「答得准」、把「像是答案」变成「有证据的答案」、把幻觉风险尽量压低（限制模型只能基于检索证据作答，并在证据不足时如实说明）

⚠️ 未给：向量库 / OpenSearch / Redis / Reranker 的具名产品与版本、RRF 的 k 参数、Top-K 与保留 8 的取值依据、Cross-encoder 模型名、缓存相似度阈值与 TTL、真实延迟分布。0.96/0.93/0.88 是图面示意分数，不是实测。
