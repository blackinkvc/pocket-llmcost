量化与蒸馏

量化省显存与带宽，蒸馏省参数与步数，两者常被混为一谈。经验上 8 位几乎无损，4 位在数学、代码和长链推理上更容易掉点，能不能接受要用自己的任务测。

两者常被混为一谈，其实目标不同：量化省显存与带宽，蒸馏省参数与步数。

手段做什么主要收益主要代价
FP16 / BF16半精度权重通用基线显存占用最大
FP88 位浮点显存减半，精度损失小需要硬件与框架支持
INT8 / INT4整数量化 + 缩放显存显著下降，decode 提速低比特下细节与长链推理退化
GGUF面向 CPU / 混合推理的格式本地部署友好，可按层量化生态以 llama.cpp 为主
AWQ / GPTQ面向 GPU 的权重量化推理吞吐高需要校准数据
蒸馏大模型教小模型，或多步教少步小模型接近大模型，步数下降上限受教师与数据限制

量化到底在省什么

回到 decode 的性质：每生成一个 token 要把全部权重读一遍。 权重从 16 位压到 4 位，读的字节变成四分之一，速度就快——所以量化主要加速 decode，对 prefill 影响小。

显存方面，权重占的部分直接降到四分之一，但 KV Cache 不会跟着降（除非单独做 KV 量化）。 长上下文场景下，这可能意味着量化后还是装不下同一条长请求。

「4 位能用吗」

经验上，8 位量化几乎无损；4 位在通用对话上可接受，但在数学、代码和长链推理上更容易掉点。

这句话的重点是看任务：同一个 4 位模型，做闲聊毫无差别，做多步代码修改可能明显变差。 所以本站不写「4 位相当于损失 X%」，没有通用数字，只有你的任务上的数字。要判断就自己跑一遍同一批任务，对比通过率。

蒸馏的两条线

语言侧：大模型教小模型，让小模型学的不只是答案，还有整个输出分布。效果是小模型接近上一代大模型。 扩散侧：把多步去噪蒸馏成少步，4–8 步出图。代价是细节和多样性略降。

两条线共同的限制：学生不可能超过老师，能接近就已经是很好的结果。
