Kafka 双队列：ingest.live / ingest.backfill

削峰填谷、解耦（上传/解析/向量化分阶段独立扩缩容）、可重试、可观测（lag 看积压）；三类消费者：解析 Worker / Embedding Worker / 写入

— 平台：消息队列（MQ）；ingest.live 承载实时上传

⚠️ 图面明确「按 doc_id 分区保持局部顺序，但不等于整个系统天然全局有序」；队列不是为架构好看，是为高吞吐写入、失败恢复与资源隔离。见 T050

5 类存储职责分离（S3 / Postgres / 向量库 / OpenSearch / Redis）

不同数据的访问方式不同，各做各的事；封面补：向量库分片存储 + ANN 检索、Postgres 存 ACL / 任务状态、Redis 语义缓存 / 热点查询

— 平台：对象存储放原始文件与解析结果；Postgres 管元数据/ACL/任务状态/版本；

⚠️ 图面三条「为什么不能只用向量库」：原始文件不适合进向量索引、关键词与结构化元数据各有擅长、热点缓存/任务状态/权限不是向量库强项；并注明「中小规模可合并技术栈，不是固定答案」。见 T051

文档加工流水线（OCR → 切块 → 元数据 → Embedding GPU 批处理）

元数据含 doc_id / chunk_id / version / 来源路径 / page_no / 段落位置 / tenant_id / 权限 / 时间戳；

— 平台：对象存储 S3 / OSS → OCR 抽标题结构/正文/表格/链接 → 切块

⚠️ 图面结论「真正决定效果和成本的是这条加工流水线本身，不是 LLM 回答」；Chunk 800/1024/768 tokens 为示意值。未给 OCR / Embedding 具名模型与重叠大小。见 T050

混合检索 + RRF 融合（向量 Top100 ∥ BM25 Top100）

向量擅长语义相似与表达变化，BM25 擅长产品名/术语/版本号/错误码；RRF 不强行比较不同分数的绝对值，保留更稳的候选集合；检索阶段就带 ACL / tenant filter

— 平台：向量库语义召回 + OpenSearch 倒排 BM25 关键词召回；

⚠️「不要等内容进了 Prompt 再删」；图面提醒海量场景最怕「本来有答案，但系统根本没把它找出来」。Top100 为设计取值，未给 RRF 的 k 参数。见 T051

Cross-encoder 重排 + 保留前 8 + Grounded Prompt

Prompt 示例：「请基于以下检索到的证据回答问题，只使用这些证据中的信息；若证据不足，请明确说明。请在回答中标注引用：[证据1][证据2][证据3]」；

— 平台：约 100 个候选片段 → Cross-encoder 逐条打分 → 保留前 8

⚠️ 图面示意分 0.96/0.93/0.88 属示意值；「不是越多越好，上下文过长会抬高成本、稀释重点」。把「找得到」变成「答得准」、压低幻觉。见 T051

生产保障四层（Golden Set / P95 / lag / DLQ / shadow index / alias

从「搭起来」到「长期跑住」；与 T050 的 DLQ、T051 的 ACL 尽早过滤、T049 的 <2 秒 P95 设计目标三处互相对上

— 平台：质量评测：Golden Set 500+ 真实问题、Recall@20 / 命中率

⚠️ 所有指标只有名字与流程、没有任何实测值；Golden Set 500+ 是图面给出的设计规模。图面结论：生产级 RAG 不是把向量库接到 LLM 就结束。见 T052

向量量化三档估算：820GB / 205GB / 26GB

另有四类额外开销：元数据约占向量本体 10%–30%、HNSW/IVF 索引结构、常见 2–3 副本成倍增加、缓存与热数据常驻内存；

— 作者：AI Agent 领域（图面估算，非具名工具） · 平台：以 2 亿向量 × 1024 维为例：Float32 每向量约 4 KB →

⚠️ 全部是图面估算值 / 设计目标，不是实测；图面自己写「真实系统的总资源消耗通常更高」，Int8「体积明显降低但不是零成本」、1-bit「需在检索效果与复杂度间权衡」。按 T038 第三类标注，见 T049
