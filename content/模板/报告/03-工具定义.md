## 单工具骨架

```json
{
  "name": "search_orders",
  "description": "按订单号查询订单状态。仅当用户提供了订单号、且问的是物流或退款进度时使用；用户只说商品名时先调 search_products。",
  "input_schema": {
    "type": "object",
    "properties": {
      "order_id": { "type": "string", "description": "订单号，形如 SO-2026-000123" },
      "fields": {
        "type": "array",
        "items": { "enum": ["status", "logistics", "refund"] }
      }
    },
    "required": ["order_id"]
  }
}
```

## 五条写法规矩

- **边界写进 description。** 「什么时候别用」比「什么时候用」更能减少误调用；模型不缺正面例子，缺的是排他条件。
- **参数要收敛。** 枚举优于自由文本，格式样例优于描述；`"2026-11-23"` 写进 description 比写「日期字符串」有用。
- **必填项越少越好。** 必填项每多一个，模型编造参数的概率就上一档。
- **一个工具只做一件事。** `do_everything` 这类工具会让模型在参数里做决策，而参数是最难自纠的地方。
- **返回也要设计。** 返回 200 行 JSON 等于把上下文预算烧掉；只回模型判断所需字段，细节让它再查一次。

## 复制这张检查表

```text
| 工具 | 单一职责 | description 写了排除条件 | 参数枚举 | 必填 ≤ 3 | 返回字段 ≤ 5 | 失败时的提示 |
| --- | --- | --- | --- | --- | --- | --- |
```

## 最容易踩的坑

**把工具名写成内部函数名。** `q_ord_v2` 对模型是零信息；名字本身就是提示词的一部分，`search_orders` 比任何注释都有效。
