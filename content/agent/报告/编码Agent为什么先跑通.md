编码是第一个真正跑通的 AI 应用场景，不是因为它最简单，而是因为**它是唯一一个自带判卷人的场景**。

## 判卷人理论

模型输出的对错，需要一个独立于模型的东西来判定。多数场景里没有这个东西，于是只能靠人看——成本高、慢、而且看不全。
代码不一样：

- 编译器会说语法对不对。
- 测试会说行为对不对。
- 版本控制会说这次改动动了哪些地方、能不能退回。

三者加起来的反馈是**免费、即时、可重复**的。Agent 不需要一次做对，它可以编译、报错、改、再编译——循环本身就是它的能力放大器。

对比一下办公场景：写一份周报，对错由谁判？写一封邮件给客户，语气合适不合适由谁判？没有判卷人，Agent 就只能「一次成型」，失败率自然高出一个量级。

## 2026 年的编码产品线已经分层

| 形态 | 代表 | 分工 |
| --- | --- | --- |
| 编辑器补全 | GitHub Copilot | 打字级别的加速，人不离手 |
| 编辑器内 Agent | Cursor | 多文件改动，人看着改 |
| 终端 Agent | Claude Code | 读写整个仓库，人只审 diff |
| 云端并行 | Codex | 扔一堆任务进去，回来收补丁 |
| Agent 平台 | Google Antigravity | 编辑器、终端、浏览器放进同一个循环 * |

分层的依据不是模型强弱，而是**人介入的位置**：从「每行都看」到「只看 diff」到「只看结果」。介入越靠后，对判卷机制的依赖越强——这也是为什么云端并行只在测试完备的仓库里好用。

## 开源模型在这一层追得最快

2026 年 7 月，Kimi K3 以开放权重登上 Arena 的编码榜首位。这件事的意义不在于「开源超过闭源」，而在于：**编码是最容易被验证的任务，而可验证的任务最容易被针对性地训练**。
代码有标准答案，能自动构造训练与评测数据；写作与咨询没有，只能靠人偏好，进步就慢得多。

## 办公场景缺的三样东西

1. **判卷人。** 文档质量没有单测，只能靠人读。
2. **权限模型。** 让 Agent 改一份合同，出错的代价与改一段测试代码不是一个量级。
3. **可回滚。** 代码有 git，文档协作里没有等价的「退回上一次」的通用机制（虽然有版本历史，但没人敢让 Agent 直接写生产文档）。

三样补齐任意两样，办公场景才会出现「编码 Agent 那个级别」的渗透率。目前看，先补的是第 3 样（版本历史 + 审批流），第 1 样最难。

## 对个人的启示

如果你要判断一个 AI 产品能不能成，先问：**它的错误由谁来发现，多久能发现，发现一次多少钱？**
三个答案都很便宜的场景，最先被 AI 吃掉；三个答案都很贵的场景，AI 只能做辅助。
