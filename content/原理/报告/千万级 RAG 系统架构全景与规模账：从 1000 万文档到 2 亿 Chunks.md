**封面全景的五个关键数字**（图面原样，均为**估算 / 设计目标**，不是实测）：1000 万文档总量、≈2 亿文本块 Chunks、≈820 GB 向量数据（Float32 估算）、≈1000 亿 Embedding Token（语料规模估算）、**<2 秒检索生成延迟（P95 设计目标）**。

**A 规模估算（第 1 张长图）**：1000 万份文档（PDF / Word / TXT / 网页等多格式）→ 平均每篇约 20 个 Chunks（切块策略如长度、重叠与文档长度决定）→ 最终约 **2 亿 Chunks**。图面强调：检索系统真正面对的不是 1000 万份文件，而是 **2 亿级检索单元**；这是向量化、建索引和检索时实际处理的基本单元。

**B 向量本体的体积估算**（以 2 亿向量 × 1024 维为例，三种表示方式并列，都是约数）：

- **Float32 · 1024 维：约 820 GB**——每个向量约 4 KB（1024 × 4 字节），2 亿 × 4 KB ≈ 820 GB
- **Int8 量化：约 205 GB**——每维由 4 字节降到 1 字节，2 亿 × 1 KB ≈ 205 GB；图面明确写「体积明显降低，**但不是零成本**」
- **1-bit 二值向量：约 26 GB**——每维 1 bit（1/8 字节），1024 维 = 128 字节/向量，2 亿 × 128 B ≈ 26 GB；代价是「通常需要在**检索效果与复杂度之间权衡**」

**C 别忽略的额外开销**（向量本体之外，四类）：① **元数据**——doc_id / chunk_id / ACL / 版本等，一般约占向量本体的 **10%–30%**，取决于字段数量与编码方式；② **索引结构**——HNSW / IVF 等向量索引也占可观空间，规模越大（图、倒排、分片元数据等）所需存储越多；③ **副本与高可用**——线上通常不止 1 份数据（多副本、跨可用区部署），常见 2–3 副本，整体存储与成本按副本数**成倍增加**；④ **缓存与热数据**——为降低检索时延会缓存热门向量、索引或查询结果，热数据常驻内存进一步抬高资源需求。

**D 嵌入成本**：粗略估算 2 亿 Chunks × 平均 500 tokens ≈ **100B tokens**（约 1000 亿），实际值随切块长度、重叠策略与文档分布变化。图面两条提醒：**嵌入不是一次性花费**——需要持续增量更新（新增 / 修改 / 删除的文档或 Chunks），随数据迭代通常还要定期重建向量与索引以控制质量与性能；**切块策略不同，Embedding 成本会明显变化**——切得更细（更多 Chunks）→ token 总量更大、嵌入成本更高；切得更粗 → 成本更低，但可能影响检索粒度与效果。

**这一页的核心结论（图面原文意思）**：千万级 RAG 的第一道门槛不是模型，而是规模带来的**存储、吞吐与成本**；这里展示的还是粗估，真实系统的总资源消耗通常更高。⚠️ 以上 820GB / 205GB / 26GB / 10–30% / 100B tokens 全部是**图面估算值**，本库按 [T038](../apps/数字的七类证据性质：演示%20·%20报价%20·%20示意%20·%20可核验计数%20·%20正文未载的图面结果.html) 第三类（示意 / 估算）标注，不写成实测性能；图里 P95 <2 秒是**设计目标**，不是达标结果。

**封面四段骨架**（与后面三张卡一一对应）：A 写入链路（文档接入 → API 网关 → 对象存储 S3 → 消息队列 Kafka → 文档处理）、B 存储层（S3 / Postgres / 向量数据库 / OpenSearch / Redis 五引擎协同）、C 查询链路（用户提问 → 查询服务 → 混合检索 → 重排器 → LLM 生成）、D 生产保障（质量评测 / 可观测性 / 索引演进 / 安全与隔离）。逐层细节见 [T050](../principles/写入链路：实时上传、历史回填、消息队列与文档加工流水线.html) / [T051](../principles/存储与查询链路：5%20类存储、查询入口、混合检索、重排与%20Grounded%20生成.html) / [T052](../principles/生产保障四层：质量评测、可观测性、索引重建、安全与权限.html)。
