本卡把 3 张图（数据接入 / 消息队列 / 文档处理）按同一条写入链路合并整理；与 [T049](../principles/千万级%20RAG%20系统架构全景与规模账：从%201000%20万文档到%202%20亿%20Chunks.html)（规模账）、[T051](../principles/存储与查询链路：5%20类存储、查询入口、混合检索、重排与%20Grounded%20生成.html)（存储与查询）、[T052](../principles/生产保障四层：质量评测、可观测性、索引重建、安全与权限.html)（生产保障）是同一系统的不同层 → 并列成卡，不硬并成一篇。

**① 两类数据进同一套系统**（第 2 张图）：

- **实时上传（接收新文档，快速纳入同一套处理链）** 4 步：用户上传 PDF / Word / 网页抓取结果等多来源 → **API 网关**负责鉴权、限流和请求转发，保证接口稳定 → 返回 **pre-signed URL 与 job_id**，前端拿到直传地址和任务编号后上传文件 → **先接收任务、再异步处理**（上传成功 ≠ 已可检索，后面还要解析、切块、Embedding 和建索引）
- **历史回填（把历史知识库平稳并入系统）** 3 步：来自 **SharePoint / Confluence / 数据库 / 内部网盘**等企业既有知识源 → 通过 **backfill 任务批量导入**，按目录、时间范围或增量规则持续同步 → 目标是把旧知识库逐步纳入统一索引体系，最终与新上传文档走**同一套后端流程**
- **统一后端处理链路**：Object Storage（统一存储上传的原始文件，新上传或历史回填）→ **ObjectCreated 事件**（文件写入后触发，通知后端开始处理）→ 进入**异步处理队列**（解析、切块、Embedding、建索引等任务异步执行，提升系统吞吐与稳定性）
- **为什么上传接口通常返回 202？** 文件已接收 ≠ 已解析完成；系统后面还要做 OCR、切块、Embedding、建索引；前台拿到 job_id 后可继续查询任务状态。图面结论：**实时上传与历史回填最好走同一套后端能力，但要在调度优先级上分开处理，避免互相挤占资源**

**② 为什么一定要上消息队列**（第 3 张图）：

- **两类流量、两种优先级**：用户上传（实时写入，要求更低延迟、尽快可检索）→ **ingest.live**（优先级更高、延迟更低、尽快被消费）；历史回填（批量导入，数据量大、可容忍更长时间）→ **ingest.backfill**（数据量更大，可按较低速率运行、可慢一些）
- **三类消费者 Worker**：解析 Worker（读取消息，解析文档内容并抽取文本）、Embedding Worker（把文本转换为向量）、写入 Worker（把向量与元数据写入向量数据库等存储）
- **消息队列的四个价值**：削峰填谷（高峰写入先存起来，按消费能力平滑处理）、解耦处理（上传 / 解析 / 向量化可分阶段独立扩缩容）、可重试（临时失败不必整条链路中断，可自动重试）、可观测（通过 **lag** 看到消息积压情况，及时评估与扩容）
- **分区与顺序**：常见做法用 **doc_id 作为分区键**分区路由到 分区 0 / 1 / 2……这样同一文档的事件更容易保持局部顺序；图面明确补了一句「**但这不等于整个系统天然全局有序**」
- **失败怎么办**：解析失败或超时 → 退避重试 → **DLQ（死信队列）** → 人工修复后可重放；多次失败进入 DLQ，目标是「不让问题文档悄悄消失」
- 结论（图面）：消息队列不是为了「架构好看」，而是让**高吞吐写入、失败恢复和资源隔离**真正落地

- **1 拉取原文件**：从对象存储（S3 / OSS 等）读取 PDF、扫描件、网页或 Office 文档；**原始文件需要保留，便于回放和后续重建**
- **2 解析与清洗**：OCR 识别图片或扫描页，抽出**标题结构（标题层级、章节）/ 正文内容（连续文本、段落）/ 表格数据（表头、表格内容）/ 链接地址（URL、内链 / 外链）**四类，清理无用噪声、统一编码与文本格式
- **3 切块策略**：常见长度 **512–1024 tokens**；图面示意 Chunk 1 ≈ 800 tokens / Chunk 2 ≈ 1,024 tokens / Chunk 3 ≈ 768 tokens；尽量保留标题上下文与段落边界；**目标不是切得越碎越好，而是兼顾召回和语义完整度**
- **4 补充元数据**：为每个 Chunk 补 doc_id（文档唯一 ID）、chunk_id（分块 ID）、**版本号 version**、来源路径（文件位置 / URL）、**页码 page_no**、段落位置（段落 / 章节序号）、**tenant_id（租户）**、权限（可见范围 / 角色）、时间戳（创建 / 更新时间）。用途：文档可追溯性、按条件过滤（租户 / 权限 / 时间范围）、后续增量更新与重建
- **5 Embedding 工人**：批量 Chunks（文本 + 元数据）→ **GPU 批处理 / 高吞吐**送入 Embedding 模型 → 结果写入向量库（向量索引），同时保留文本与元数据
- **更新与重建三条**：模型版本要记录（如 embedding 模型名、版本号），便于后续对齐、回滚与复现；文档更新后**旧 chunks 需要失效或替换**（重新解析、切块、向量化）；否则会出现旧版本内容继续参与检索（影响准确性，导致「幻觉」或过时答案）

一句话结论（图面）：千万别把「文档进库」理解成简单上传文件，真正决定效果和成本的是**这条加工流水线本身**；真正耗时的往往不是 LLM 回答，而是文档解析、切块、元数据整理和向量化。

⚠️ 图面只给架构与示意值，未给：消息队列的具体产品与分区数、重试次数与退避策略、OCR / Embedding / Reranker 具名模型、切块重叠大小、GPU 型号与批大小、DLQ 保留时长、真实吞吐。一律不补。
