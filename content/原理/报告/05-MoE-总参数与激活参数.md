混合专家（Mixture of Experts）把 FFN 拆成很多组，每个 token 只选 top-k 组计算。
于是两个数字同时存在：

- **总参数**决定显存占用——所有专家都要装进去。
- **激活参数**决定单 token 计算量——每次只算选中的那几个。

```
显存 ≈ 总参数 × bytes_per_param
计算 ≈ 激活参数 × bytes_per_param（decode 读权重）
路由：每个 token 选 top-k 专家，需要负载均衡避免塌缩
```

## 最常见的误判

看到「1T 参数」就以为需要 1T 稠密模型的算力。**不对。**
计算按激活部分走，可能只有几十 B 的量级；但显存仍要装下全部专家，所以 MoE 对显存更敏感、对算力更友好。

反过来说，「MoE 能省算力」也不等于「MoE 更便宜」：
显存贵、机器贵，一个 1T 总参数的 MoE 仍然要一整台多卡机器才跑得起来。省的是运行时算力，不是硬件门槛。

## 路由是它的软肋

每个 token 要选专家，就需要负载均衡。如果路由塌缩（大部分 token 涌向少数专家），
相当于其他专家白占显存，训练也会不稳。这是 MoE 工程实现里最麻烦的一块，比矩阵乘本身麻烦得多。

## 规格表怎么读

看到 MoE 模型，至少要看四个数：总参数、激活参数、专家数、top-k。
只写总参数的规格表，等于只告诉你「要多少显存」，没告诉你「跑多快」。
本站基模页的模型台账里，凡是标了总参数与激活参数的都分开写，就是因为这两个数经常被混成一个。
