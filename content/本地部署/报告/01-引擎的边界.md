## 先分清三件事

本地跑模型，卡点只有三个：**显存够不够、带宽喂不喂得饱、要不要多并发。**

- 显存不够 → 换更小的量化，或换更大的机器。换引擎没用。
- 带宽不够 → 单用户场景换引擎最多改善 10%–20%，瓶颈在硬件。
- 要多并发 → 这时换引擎才有数量级的差别：llama.cpp 的串行优势变成劣势，vLLM 的 PagedAttention 才是答案。

**「能跑但很慢」通常是第 2 类，「很快但装不下」是第 1 类。** 分清之后再动手，能省掉大半夜的折腾。

## 七套引擎各自解决什么

| 引擎 | 真正的长处 | 什么时候别用 |
| --- | --- | --- |
| llama.cpp / GGUF | 单机跑得动，CPU 与统一内存都能用，量化格式最全 | 需要多并发服务 |
| Ollama | 五分钟试一个新模型，带本地 API | 要压榨吞吐，或要调底层参数 |
| LM Studio | 图形界面挑模型、并排对比输出 | 要批处理、要自动化 |
| MLX | Apple 芯片上最顺的一条路 | 非 macOS |
| vLLM | 多并发吞吐，PagedAttention 省显存 | 单用户、小显存机器 |
| SGLang | 结构化输出与约束解码 | 生态小、遇到问题没人踩过 |
| ComfyUI | 节点式生图 / 生视频工作流 | 文本推理（它不是干这个的） |

## 量化格式必须和引擎配套

这是最常见的「跑不起来」原因，而不是模型坏了：

- **GGUF** 给 llama.cpp 系（Ollama、LM Studio 底层也是它）。
- **AWQ / GPTQ / FP8** 给 GPU 服务端（vLLM、SGLang）。
- **MLX 量化** 是 Apple 自己的一套，和上面都不通用。

同一个模型在 Hugging Face 上常有五六种格式，下错一个，报错信息往往只说「不支持的数据类型」。

## 三个便宜的先手

1. **先跑官方示例。** 官方 demo 跑不通，问题在环境（驱动、CUDA / ROCm 版本、Python 依赖），不在参数。
2. **固定上下文再调速度。** 上下文从 8K 开到 32K，速度掉一半是正常的，不是引擎坏了。
3. **留 15%–25% 显存余量。** 卡在 98% 占用上跑，长上下文一到就 OOM；而 OOM 往往发生在演示的时候。

## 一句话判据

**单用户追求「能跑 + 好维护」→ llama.cpp / Ollama；多用户追求「吞吐 + 成本」→ vLLM / SGLang；生图生视频 → ComfyUI。**
三件事都要，就装三套，别指望一套通吃。
