1.6 怎么读这个数 / 一个补充说明

口径提醒

Star ≠ 用户，更 ≠ 活跃使用。Fork 里相当一部分是读代码或接 SDK 的开发者；BYOK + 纯本地执行意味着哪怕真有几十万人在用，官方也统计不到。如果你是在评估要不要引入，建议把判断锚点放在「下载量、活跃贡献者数、Issue 收敛速度、是否有企业案例」上，而不是 19K Star——目前这些信号都还是早期项目形态。

02相比其他 Agent 有什么特点和优势

问题：相比其他 agent 有什么特点和优势。

2.1 一句话定位

核心判断

它的优势不是「更聪明」，而是「把控制权还给你」——OpenWorker 是少见的、把「本地优先 + MIT 开源 + 任意模型（含完全离线）+ 成品交付」四样集齐的桌面 Agent，模型能力上限其实取决于你自己带的 key。

2.2 它主动放弃了三样东西

相比同类，最干净的理解方式是看它不做什么：

放弃云端执行

对话、密钥、连接器 token 都在本机；模型调用直接从电脑发往模型厂商，不经 OpenWorker 中转。唯一上云的是 OAuth 握手，甚至可以手动填凭据完全不登录、断网也能跑。

放弃模型锁定

基于 aisuite 统一路由，OpenAI / Anthropic / Gemini / DeepSeek / Qwen / Kimi / GLM / MiniMax / Mistral / Grok 及 Ollama 都能接，换模型不改工作流、任务中途可切。

放弃全托管

不像 Manus 类云端 Agent 把执行打包在云上、用户看不到中间过程；它把「权限」当成一等公民，写文件、跑 Shell、发外部请求都要走审批流程。

2.3 六个真正拉开差距的特点

1治理是架构，不是 UI 上的确认按钮

四层边界：① 硬底线——危险且不可逆的操作永远人工专属，全自动模式也不能降格；② 逐次审批——默认逐次确认，一次批准可升级为常驻规则、再升级为配置白名单，每步可见可撤销；③ 自动批准复核——复核模型放行常规动作，不确定的交回人，连续拒绝触发熔断交还控制权；④ 执行沙箱——命令和文件工具可跑在 NVIDIA OpenShell 容器 / macOS 沙箱 / Windows 隐藏账户里，沙箱内只有本次会话文件夹、没有模型 key。每次工具调用都记录「谁批准、为什么」，可复盘而非只看最后一段自然语言解释。

2无人值守不自我批准

定时任务碰上有后果的动作，请求进收件箱等人复核，不会因为人不在就放宽权限。这点在同类里几乎独一份。

3交付成品 + 全过程记录

交回的是 brief.md、修好的 PR、可直接发出的 Slack 草稿，附带完整运行记录，而不是「你可以先看这几个线程」的一长串指引。

4跨工具广度，从代码扩展到整个工作流

25+ 原生连接器 + 任意 MCP；Slack 里 @ 一下桌面端自动起会话、结果回线程；定时晨报 / 周报。边界不是代码仓库，而是文件系统 + 终端 + 日历 + 邮件 + Jira / GitHub / Notion。

5安全 coworker 是首批专职角色

semgrep 等确定性扫描器 + 模型推理找漏洞，修复后重扫、diff 复核再交人批准——「写修复的 agent 不是唯一的检查者」。还内置把工具 / 日志 / 文件 / 外部消息一律视为不可信数据的 ops 人设，防提示注入。

6桌面 App + Harness SDK 双形态，MIT 可审计

既能开箱用，也能把 agent 循环、审批、流式会话嵌进自己的产品（TypeScript / Rust SDK）。相比自建框架，省了桌面壳、连接器、权限阶梯和沙箱适配；相比闭源产品，代码能读能 fork 能商用。

2.5 几个容易被误读的边界

  • 「本地优先」≠ 零数据外发：接云端模型时上下文仍发给模型厂商，真正全离线只有 Ollama / LM Studio / llama.cpp / vLLM 这条路。
  • 自动批准的复核是模型判断，不是硬边界：真正兜底的是硬性底线和审计轨迹，官网自己也这么写。
  • 平台与成熟度：桌面端只有 macOS / Windows（Linux 仅有 CLI），Windows 包未代码签名、仍是 open beta、400+ 未关 Issue；第三方评测只给 3.9/5，并直言「三个月大、路线图由内部清单主导」。

2.6 遥测补充与选型建议

顺带补上一轮的结论

登录后默认会发一个内容无关的启动事件（哪种 coworker、何时启动），可关闭；未登录什么都不发。这解释了为什么查不到真实使用量——它本来就不统计任务级数据。

值得试：在意隐私 / 私有化、想把 agent 权限逻辑读一遍再信任它、需要跨 Slack + Gmail + GitHub + 日历交成品，或者想用 DeepSeek / Qwen / Ollama 驱动。

还不到时候：要企业级合规与 SLA、长时间云端异步研究、纯 IDE 编码流，或完全不想配 API key。

03跟 WorkBuddy 和 Trae 对比

问题：跟 WorkBuddy 和 trae 对比。

3.1 先把「Trae」说清楚

它现在是两条线：Trae IDE / CLI（AI 编程工具）和 TraeWork（2026 年 6 月由 TRAE SOLO 更名的 AI 办公平台，Work / Code / Design 三模式）。8 月字节把 TRAE 和扣子（Coze）团队并入豆包体系，TraeWork 的能力整合进了独立品牌「豆包工作」，IDE / CLI 继续作为豆包旗下编程产品线。所以今天拿办公 Agent 对比，实际对标的是 TraeWork / 豆包工作。

3.2 结论：这不是同一量级的比较

量级

OpenWorker 是一个三个月大、19K Star 的开源 beta 项目；WorkBuddy 和豆包工作是千万 DAU、有财报和收费体系的国民级商用产品。先看规模，差距大概三个数量级。

产品公开规模数据
WorkBuddy（腾讯）日活超 1000 万；日均 Token 消耗超 100 万亿；累计 90 亿次任务请求；9 月 MAU 3235 万；6 月单月访问量 2097 万次（超第二、三名总和）；近七天年化收入超 5 亿美元；企业版落地 50+ 行业、覆盖半数中国 500 强 / 60% 中国 100 强；腾讯内部超 12000 名员工常态化使用。
Trae / 豆包（字节）TraeWork 2026 年 6 月注册用户破 1000 万、企业客户超 1 万家、日均 Token 5.6 万亿；6 月国内访问量 1279 万排第二；豆包工作上线三个月 DAU 破 800 万、企业客户 ARR 破 20 亿元；TRAE 在国内 AI 编程市场份额 41.2%，个人用户数百万量级；豆包 App 2026 年 6 月月活 3.82 亿。
OpenWorker19,426 Star（11/18）、open beta、413 个未关闭 Issue；官方没有中心化遥测，压根不公布使用量。

正呼应上一轮——不是查不到，是它设计上就不统计；而这两款国内产品的规模是公开可查的。

3.3 五个维度，差异在哪

① 开源与「谁掌握控制权」

OpenWorker 是 MIT，代码可读、可 fork、可商用，权限逻辑能逐行审计；WorkBuddy 官方未发布源码或开源许可，TraeWork 也是闭源。后两家给的是「厂商开放给你的管控」——WorkBuddy 企业版有审计日志、SSO、私有化 / VPC，TraeWork 企业版有企业级沙箱策略、SSO、Hook——但底层不归你。

② 数据落在哪

OpenWorker 最彻底：agent 循环、对话、连接器 token、模型 key 全在本机，唯一上云的是一个可跳过的 OAuth 握手，接 Ollama / vLLM 可完全离线。WorkBuddy 默认本地沙箱 + 授权目录、高危操作前确认，但也提供纯云端 Managed Agents。TraeWork 是双轨：本地任务项目目录可写、受保护目录只读；云端任务跑在独立沙箱容器里、碰不到宿主机文件系统（macOS 的 Work / Code / Design 与 Windows 的 Code 模式适用；Windows 的 Work/Design 用隔离虚拟化运行环境，仅能读写当前项目目录）。

③ 模型自由度

  • OpenWorker 完全厂商无关：OpenAI / Anthropic / Gemini / DeepSeek / Kimi / Qwen / GLM / MiniMax / Mistral / Grok，加 Together / Fireworks，再到 Ollama 全离线，换模型不改工作流。
  • WorkBuddy 其实也很开放：混元 Hy3 / Hy4flash、DeepSeek、GLM、Kimi、MiniMax 等十几个模型，可填自己的 API key，也支持 Ollama，只是出于竞争没接百度 / 阿里 / 字节的模型。自选模型用户中选择 Hy3 的占比曾达 60% 以上。
  • TraeWork 以豆包（Doubao-Seed 系列）为主，内置 GLM、Kimi、MiniMax，可自定义接 DeepSeek，海外版才支持 GPT / Gemini。
顺带纠个偏

网上早期那篇「三条路线」评测把 WorkBuddy 写成「绑自家模型、跑云端」，已经和 2026 年下半年的官方形态对不上了。

④ 审批治理的颗粒度

这是 OpenWorker 唯一明显领先的地方：硬底线（不可逆操作永远人工专属）→ 逐次审批可升级为常驻规则 / 白名单 → 自动批准的复核模型 + 连续拒绝熔断 → OpenShell 沙箱，每次工具调用都记「谁批准、为什么」，无人值守任务把请求停进收件箱而不是自行放行。

WorkBuddy 是 Ask / Plan / Craft 三档 + 高危指令拦截 + 操作留痕；TraeWork 是 Plan 逐步弹窗 / Go 全自动，甚至有命令白名单绕过沙箱、自动运行跳过确认的模式。后两家更偏「够用且省心」，不是「可回看的行动边界」。

⑤ 生态与开箱即用——国内用户最致命的一条

  • WorkBuddy：打通企业微信、腾讯会议、腾讯文档、乐享、ima，微信 / 企微 / QQ / 飞书 / 钉钉手机端远程派活；100+ 专家和技能包、资料库、人机双写、多 Agent 并行；开放平台首批超百家生态伙伴。
  • TraeWork / 豆包工作：Work / Code / Design 三模式在同一 Workspace 接力、桌面 / 网页 / 移动三端同步、飞书深度打通、200+ 技能与连接器；豆包工作支持多 Agents 并行，并可从 ChatGPT / Claude Code / Trae Work 迁入任务偏好、技能、连接器、工作记忆和历史会话。
  • OpenWorker：25+ 连接器清一色海外 SaaS（Slack、Gmail、Jira、Notion、Linear、HubSpot、Outlook、Google Calendar、Attio、Stripe、Figma 等），飞书、钉钉、企业微信一个都没有；界面全英文、无 i18n 框架，语音只认英文，社区汉化包得自己打。它的演示场景（Slack 里 @ 一下派活、Gmail 准备续约电话）在国内基本不成立。

3.4 成本

产品计费方式
OpenWorker软件免费（MIT），只付模型 token；接 Ollama 可为零成本；模型用量由所接供应商计费。
WorkBuddy体验版月送 500 积分；个人标准 ¥99/月、高级 ¥199/月、旗舰 ¥999/月（连续包月 ¥70 / ¥140 / ¥700）；企业旗舰版 198 元/人/月、企业专享版 316 元/人/月（100 席位起购）；Credit 可单独加购；Hy4flash 等有限时免费。
TraeWork积分计费，新用户每月赠送 500 积分；简单对话消耗低，多步骤 Agent、大型工程调试、代码运行会快速消耗积分；高峰期有排队机制，付费档优先响应。

3.5 怎么选

OpenWorker
要读代码、要完全离线、要把 agent 循环嵌进自己产品、要做安全审计 / 权限原型 → 只有它满足；代价是自己配 key、自己接国内工具、忍受 beta 坑（自定义 OpenAI 兼容接口报错、订阅账号不认、Linux 无桌面包等）。
WorkBuddy
国内职场日常交付（周报、PPT、表格）、想用微信远程指挥电脑、需要企业合规和售后 → 成熟度当前领先；短板是画图仍扣积分、白天高峰排队。
TraeWork / 豆包工作
产研一体、代码 + 数据 + 设计一条链、飞书重度用户 → 编码基因最厚；但 PPT 版式美感和定时任务稳定性（电脑息屏会中断）被评测吐槽过。
一句大白话

OpenWorker 赢在「自由与可审计」，输在「生态、成熟度、省心」。如果是想给团队换生产工具，现在国内这两款更现实；如果是想搞清楚「Agent 的权限到底该怎么做」，把 OpenWorker 的 README 读一遍，比用哪款产品都值。

4.3 阅读本报告时的三个注意点

  1. 代理指标不等于使用量：GitHub Star / Fork / PR 反映的是开发者关注度，不等于装机量、活跃用户或任务完成数。
  2. Beta 项目变动快：OpenWorker 仍处于开放测试，接口、平台支持（尤其 Windows 签名、Linux 桌面包、中文化）与连接器列表可能快速变化。
  3. 对比是「站位」而非「排名」：三款产品的设计哲学不同（自由可审计 / 开箱省心 / 工作流深度），适用场景差异大于能力高低，选型应先看自身生态绑定与合规要求。
